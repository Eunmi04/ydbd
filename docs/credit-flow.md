# 테스트 크레딧 운영 규칙 (1단계)

이 문서는 캡스톤 시연용 도메인 계약이다. 구현 기준은 [상태 전이](state-machine.md)와 [팀 간 데이터 계약](api-contracts.md)을 함께 따른다. Supabase 모드의 SQL/RPC와 앱 호출 코드는 작성됐지만 실제 DB 적용·통합 실행은 아직 검증되지 않았다. 환경변수가 없는 경우 기존 메모리 시연 모드가 남아 있다.

## 범위와 용어

- 크레딧은 시연용 정수 단위다. 실제 돈의 충전, 환급, 현금화, 사용자 간 송금, 방장에게 지급하는 기능이 아니다. 실제 택시비는 방장이 기사에게 직접 결제한다.
- `available_credit`은 사용자 거래 원장의 `amount` 합계다. 별도의 잔액 값을 직접 변경하지 않는다. `held_credit`은 `HELD` 예치의 `amount` 합계이며, 화면에 총량이 필요하면 `available_credit + held_credit`으로 표시한다.
- 모든 원장 금액은 정수다. `TEST_GRANT`, `ROOM_RELEASE`는 양수, `ROOM_HOLD`, `SETTLEMENT_DEBIT`은 음수다. `ADMIN_ADJUSTMENT`는 개발 환경에서만 허용하며 사유와 실행자를 기록한다.
- 거래 원장은 추가 전용이다. 일반 사용자의 직접 생성·수정·삭제를 허용하지 않는다. 오류 정정도 기존 행을 고치는 대신 별도의 조정 거래로 기록한다.
- `room_credit_reservations`의 `NONE`은 행이 없다는 조회 결과이며 DB에 저장하는 예약 상태가 아니다. 저장되는 상태는 `HELD`, `RELEASED`, `CAPTURED`다.

## 참여, 준비, FIX

1. 방 참여만으로 예치하지 않는다. `READY_CHECK`의 참여자가 준비 요청을 할 때 서버가 예치와 `READY`를 한 작업으로 처리한다. 동일 요청 재시도는 저장된 결과를 반환한다.
2. 예치 가능 조건은 인증된 이용 가능 계정, 방 참여자, `READY_CHECK`, 동일 방의 활성 예치 없음, 충분한 사용 가능 크레딧이다. 금액은 서버가 `max(5000, ceil(estimated_fare / max_members / 1000) * 1000)`으로 계산한다. 클라이언트 금액을 받지 않는다.
3. 방장은 `OPEN`에서 최소 인원 이상일 때 준비 확인을 시작한다. 서버는 그 시점의 참여자를 준비 대상자로 고정하고 `READY_CHECK`로 바꾸며 `ready_started_at`과 `ready_deadline_at = ready_started_at + 30초`를 기록한다. 이후 신규 참여와 자발적 탈퇴를 막는다.
4. 준비 요청은 서버 시간 `now() < ready_deadline_at`에서만 성공한다. 앱의 카운트다운과 기기 시간은 표시용이다. 준비 대상자 전원이 `READY`이고 예치가 `HELD`이면 마지막 준비 요청을 처리하는 같은 작업에서 `FIXED`로 전환한다. 인원수는 방의 `min_members` 이상 `max_members` 이하이어야 한다.
5. 마감 시각까지 조건을 만족하지 못하면 방을 `CANCELLED`로 만들고 모든 `HELD` 예치를 반환한다. 앱이 꺼져 있더라도 이후 첫 서버 요청에서 만료 여부를 검사·정리한다. 마지막 준비 요청을 서버가 마감 전에 받아 검증했다면 같은 원자적 작업에서 FIX한다.
6. `FIXED` 이후 일반 사용자의 신규 참여, 탈퇴, 준비 재요청, 예치 변경은 허용하지 않는다.

## 취소와 반환

- `OPEN`, `READY_CHECK`의 방 전체 취소는 방장이 요청한다. 준비 확인 기한 만료는 관련 서버 요청 시 자동 정리된다. 자발적 탈퇴·운영자 취소는 이번 캡스톤 RPC 범위가 아니다.
- `FIXED`에서는 택시 이용 시작 전 방장 또는 운영자만 방 전체를 취소할 수 있다. `IN_PROGRESS` 이후 일반 취소는 없다.
- 방 전체 취소는 방 상태 전환과 모든 `HELD` 예치의 `ROOM_RELEASE +예치금`, 예약 상태 `RELEASED`를 하나의 원자적 작업으로 처리한다. `room_members` 행은 감사 기록으로 남으며 방 상태만 `CANCELLED`가 된다. 이미 `RELEASED` 또는 `CAPTURED`인 예치는 다시 반환하지 않는다.

## 탑승, 이의 및 정산

- FIX된 모든 대상자는 `BOARDED` 또는 `NO_SHOW`를 직접 기록한다. `UNKNOWN`이 하나라도 남으면 요금 제출을 거부한다. `NO_SHOW`의 분담금은 0, 예치금은 전액 반환 대상이다. 단, 이 사용자도 본인의 정산 내역을 확인해야 하므로 자동 차감·반환은 하지 않는다. 미탑승 여부에 이의가 있으면 정산 확인 화면에서 `DISPUTED`로 보류한다. 본인 신고만 쓰는 것은 캡스톤 시연 정책이며, 실제 서비스에서는 검증이 필요하다.
- 방장이 실제 요금과 개인정보를 가린 샘플 증빙 설명을 제출하면 동승자 확인을 연다. 방장의 제출은 방장 본인의 요금 확인으로 간주하고, 나머지 확정 참여자(미탑승자 포함) 전원의 현재 `settlement_version` 확인이 필요하다. 이의가 있으면 `DISPUTED`로 보류한다.
- 최초 요금 제출의 `settlement_version`은 1이다. 이의가 생기면 방장이 요금·증빙을 수정해 확인을 다시 열면서 버전을 1 증가시키고 이전 확인을 모두 무효화한다. 요금 제출 전 정산 레코드는 만들지 않는다.
- 서버가 FIX 대상, 탑승 확인, 현재 버전의 요금 확인, `HELD` 예치를 조회하여 정산 대상을 정한다. 클라이언트가 보낸 인원 목록·인원수·분담금을 신뢰하지 않는다. `actual_fare`는 양의 정수다. 탑승자별 기본 분담금은 정수 나눗셈 몫이고 나머지 1씩은 `joined_at, member_id` 순서의 탑승자에게 배분한다. 미탑승자는 0이다.
- 어느 참여자라도 `share > reserved_amount`이면 `FARE_EXCEEDS_RESERVED_CREDIT`로 정산을 중단한다. 자동 추가 예치나 음수 잔액은 없다.
- 요금 제출 때 사용자별 `settlement_items`를 만들고, 최종 정산 때 탑승자 지갑에는 `ROOM_RELEASE +reserved_amount`, `SETTLEMENT_DEBIT -share`, 미탑승자에게는 `ROOM_RELEASE +reserved_amount`만 기록한다. 탑승 예치는 `CAPTURED`, 미탑승 예치는 `RELEASED`다. 방과 정산의 완료까지 하나의 원자적 작업이다.
- 예: 네 명이 각각 5,000을 예치하고 실제 요금이 12,000이면 1인 분담금은 3,000이다. 각 사용자 원장에는 예치 시 `ROOM_HOLD -5,000`, 정산 시 `ROOM_RELEASE +5,000`, `SETTLEMENT_DEBIT -3,000`이 남는다. 예치 직전과 비교한 최종 사용 가능 크레딧 감소액은 3,000이다.

## 중복 요청과 서버 일관성

- 모든 변경 요청은 호출자가 생성한 UUID `request_id`를 받는다. 같은 사용자·같은 ID·같은 작업·같은 입력은 기존 결과를 반환한다. 같은 ID로 작업이나 입력이 바뀌면 `REQUEST_ALREADY_PROCESSED`를 반환한다. 요청 결과와 입력 지문을 저장해야 하므로 원장과 별도로 요청 이력 저장소가 필요하다.
- 예치·반환·정산의 원장 키는 사용자와 비즈니스 동작별로 고유해야 한다. 같은 방에 재참여할 수 있으므로 예치 시도별 예약 ID를 포함한다. 예: `reservation:<reservation_id>:hold`, `reservation:<reservation_id>:release`, `settlement:<settlement_id>:debit:<user_id>`. 정산의 반환과 차감은 서로 다른 키다.
- 서버 RPC는 지갑 행 잠금 후 사용 가능 잔액 계산, 동일 방·사용자의 활성 예치 고유 제약, 원장 키 고유 제약, 방·정산 상태 조건부 전환을 적용한다. 다수 지갑은 사용자 ID 순서로 처리한다. 화면 버튼 비활성화는 보조 수단일 뿐이다.
- 서버가 처리한 상태와 거래 원장이 불일치하면 부분 성공으로 응답하지 않는다. 원자적 작업 전체를 실패시키고 재요청할 수 있게 한다.

## DB 대상

핵심 테이블은 `credit_wallets`, `credit_ledger`, `room_credit_reservations`, `settlements`, `settlement_items`다. 동일 요청의 결과 재생과 입력 지문 비교에는 `idempotency_requests`를 사용한다. 구현 파일은 `supabase/migrations/202610140001`~`011`이다. 실제 DB 적용·RLS 검증은 아직 필요하다.
