# 실제 서비스 시연 준비와 검증

## 이번 변경

- 마이페이지에서 닉네임·학교명을 `profiles` 본인 행에 저장하고 DB 응답으로 화면을 갱신한다.
  이메일·인증 상태·계정 상태·시연 표시·크레딧은 수정 요청에 포함하지 않는다.
- 방 생성은 기존 `create_room` RPC를 그대로 사용한다. `ACTIVE / UNVERIFIED` 계정으로 생성·참여 가능하다.
  `rooms` 직접 INSERT 권한을 부여하거나 `VERIFIED` 조건을 추가하지 않는다.
- 방 생성 화면의 과거 시각이 될 수 있는 고정 기본값 `18:30`을 현재보다 1시간 뒤로 바꿨다.
  날짜 선택과 빈 시간 입력 검증, 중복 제출 방지, 오류 안내도 보완했다.
- 지도는 기존 문자열 출발지·목적지 미리보기를 유지한다. 기존 6개 RPC 인자와 화면 입력이 일치하며,
  지도 좌표는 RPC의 필수 인자가 아니므로 미입력을 이유로 생성을 막지 않는다.
- 요청 ID 저장 키를 로그인 사용자별로 구분하고, 요청 직전 계정 변경을 확인한다.
- 홈·방 목록·방 상세·탑승·정산 화면은 보이는 동안 3초마다 서버 상태를 갱신한다.
  30초 준비 기한, 다른 사용자 준비·탑승·요금 제출·확인을 서로 볼 수 있도록 했다.
- 지갑 충전 UI·기존 로컬 시연·지도 기능을 삭제하지 않았다. TEST 크레딧 지급은 기존 관리자 seed 방식이다.

## 지정한 시연 계정만 준비

사용자가 지정한 계정은 `1234@gmail.com`, `5678@gmail.com`이다.
두 계정은 먼저 앱에서 정상 가입되어 있어야 하고 `account_status=ACTIVE`여야 한다.
비밀번호는 채팅에 보내지 않는다.

1. 기존 `001~013`을 다시 실행하지 않는다.
2. SQL Editor에서 새 `supabase/migrations/202610210014_demo_verification_marker.sql`을 실행한다.
   시연 표시 열과 관리자 전용 원상복구 백업 테이블만 추가하며 사용자 인증·잔액은 바꾸지 않는다.
   열이 이미 있다는 오류에 대비해 이 새 파일은 재실행이 가능하도록 작성했다.
3. `supabase/seed/demo_two_accounts.sql`을 실행한다.
   위 이메일 두 개가 모두 존재하고 ACTIVE인지 먼저 검사하고, 지정된 두 계정만
   `VERIFIED`, `demo_verification=true`로 변경한다. 실제 본인 인증을 수행했다는 뜻이 아니다.
   각 계정에 TEST 크레딧 20,000P를 기존 `TEST_GRANT` 원장 방식으로 지급한다.
   같은 seed를 반복 실행해도 같은 지급 키로 크레딧이 중복 지급되지 않는다.
4. 앱을 새로고침하거나 재로그인하고 마이페이지의 **시연용 인증 상태 · 실제 본인 인증 아님** 표시를 확인한다.
   다른 신규 회원은 계속 `UNVERIFIED`다. 사용자는 이 열과 인증 상태를 직접 변경할 수 없다.

014는 새 DB 구조이고, seed는 지정 계정에 실제 영향을 주는 관리자 작업이다.
로컬 SQL 파일을 저장한 것만으로 원격 DB에 적용되지는 않는다.

## 시연 순서

두 브라우저의 로그인 저장소가 섞이지 않도록 일반 창·시크릿 창 또는 서로 다른 기기를 사용한다.

1. 신규 가입·로그인 → 마이페이지 닉네임·학교명 저장 → 새로고침·재로그인으로 유지 확인.
2. A(`1234@gmail.com`)로 미래 출발 시간의 방을 생성한다. 최대 인원 2명, 예상 요금 10,000원을 사용하면
   각자 예치액이 5,000P다. B(`5678@gmail.com`)로 목록에서 같은 방에 참여한다.
3. 두 계정 모두 같은 방 상세 화면을 연 뒤 A가 **30초 준비 확인 시작**을 누른다.
   두 계정에서 **준비 완료 · 5,000P 예치**를 30초 안에 누른다. 화면은 약 3초 내 갱신된다.
4. 방 확정 후 두 계정 모두 탑승 완료를 누른다.
5. A가 실제 요금 8,000원과 샘플 증빙 설명을 제출한다. 기존 SQL은 제출한 방장 항목을 자동 확인한다.
6. B가 **요금·탑승 정보 확인**을 누른다. A가 **모든 참여자 확인 후 정산 확정**을 누른다.
7. 정산 결과와 두 계정의 지갑을 확인한다. 각 4,000P 차감, 예치 해제 후 HELD=0이어야 한다.
   실제 결제·송금은 발생하지 않는다.

## 지정 계정으로 실제 RPC 전체 검증

아래 명령을 **본인 로컬 터미널**에서 실행하면 두 계정 비밀번호를 가린 상태로 입력받는다.
비밀번호·토큰을 파일이나 로그에 저장하지 않고 종료 시 임시 환경변수를 제거한다.
채팅에 비밀번호를 보내거나 `.env`에 비밀번호를 추가할 필요는 없다.

```powershell
cd mobile
powershell -File scripts/Check-DemoFlow.ps1
```

이 검증은 지정 계정으로 실제 로그인한 뒤 실제 방·예치·정산을 생성하므로 두 계정에서
각 4,000 TEST 크레딧이 소비된다. 성공 단계와 방·정산 ID를 출력한다.
중간에 실패하면 출력한 단계·오류 코드를 확인한다.
OPEN/READY_CHECK/FIXED 단계 실패는 가능한 경우 방 취소·예치 반환을 수행한다.
탑승 이후 중단한 방은 출력된 ID로 확인하여 기존 정산 흐름을 마쳐야 한다.
이 스크립트는 화면 자체를 검사하지 않으므로 위의 두 창 시연도 별도로 확인한다.

## 시연 뒤 인증 상태 되돌리기

먼저 진행 중인 방을 정산 완료하거나 탑승 전 취소하여 HELD 예치를 해제한다.
SQL Editor에서 `supabase/seed/restore_demo_two_accounts.sql`을 실행한다.
백업한 두 계정의 원래 인증 상태와 시연 표시만 복구한다.
HELD가 남아 있거나 다른 관리자가 인증 상태를 바꿨으면 무조건 덮어쓰지 않고 중단한다.
프로필에서 직접 수정한 닉네임·학교명은 유지한다.
원장·정산 기록과 지급된 TEST 크레딧은 삭제하지 않는다. 크레딧 회수가 필요하면
남은 예치·사용 내역을 확인하여 별도의 관리자 조정 원장으로 처리한다.
